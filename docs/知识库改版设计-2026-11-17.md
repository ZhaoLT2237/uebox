# 知识库下线，改成项目里的知识文件

> 状态：设计稿，未动代码 · 2026-11-17

## 一句话

「知识库」这个功能整个下线。项目知识改成**项目目录里的几份 Markdown 文件**，由助手用现有的读写文件工具来写、改、查。开场时，助手会读到这些文件的目录。没有单独的页面、数据库、切片检索，也不用向量模型。

## 打个比方

现在的知识库是一座**图书馆**，盖在项目外面：用户要专门进馆、自己搬书，馆员每次只翻出 5 段剪报。

改成之后，它是**项目文件夹里的一本交接手册**。它跟着项目走：拷工程、提交版本库、给同事，手册都一起带上。老员工每做完一块就改对应那页，新人进来先看目录。翻手册不需要专门的馆员，谁都能直接打开读。

Claude Code 的 CLAUDE.md、Cursor 的 rules、AGENTS.md 都是这个路子：知识放在项目里，是纯文本，由 Agent 维护。

## 为什么这么激进

1. **用的人太少。** 外部大约 1000 个用户里只有 10 个在用，本机也一样（数据见下）。为 1% 的用户维护一个独立页面、一套检索、一个工作室，不值。
2. **少数真实用法，要的都是项目记忆。** GoldTown 那次，用户的原话是：「工程里东西太多，我自己都记不全。你给这个工程建一个知识库，后面做功能都先查它。」项目记忆就该放在项目里。
3. **文件天生能解决现有的四个毛病**，见下表。

| 现在的毛病（GoldTown 实测） | 换成文件之后 |
|---|---|
| 只能加不能改，写错了只能追加一条「更正」，下次两条一起命中 | 直接编辑那一页 |
| 同一篇存进两个库；标题差一个字就新建一个库 | 一个项目只有一个文件夹，同主题就是同一个文件 |
| 检索词是一长串关键词、`limit` 开到 30，其实是想读整页 | 先看目录，再整页读，或者用全文搜索 |
| 每次都要用户叮嘱「先查知识库」 | 开场环境里自带目录 |

多出来的好处是**团队共享不用另做**：文件进 Git 或 Perforce，同事拉下工程就有了。

## 新形态

### 文件放在哪

```
<UE 项目根>/
  UEBox/
    README.md        ← 目录：每页一行标题加一句话，再加几条最要紧的项目约定
    战斗系统.md
    村民与对话.md
    性能排查.md
    ...
```

- 放在项目根下的 `UEBox/`，**不放进 `Content/`**：UE 不会去扫，打包也不会带上。
- 文件夹名看得见，用户才会注意到它、愿意把它提交进版本库。
- 只有用户说了「记下来」「给工程建知识」，助手才会建这个文件夹。不替用户自作主张往工程里写文件。

### 助手怎么用

**工具数 −2**：`search_notebook_sources` 和 `add_notebook_source` 删掉，改用已有的 `read_local_file`、`write_local_file`、`edit_local_file`、`grep_local_files`。

- **开场**：对话归属的项目里有 `UEBox/README.md`，就把它放进 `<environment>`，紧挨项目名和引擎版本。会话中途不更新这一段，免得打碎提示缓存。
- **写**：用户让记时写。另外，`UEBox/` 已经存在时，助手做完一块功能、改了项目做法或发现已知问题，就更新对应那页和 README 目录。同一主题改原文件，不新建。
- **查**：先看目录，再读整页；目录里没有的就 `grep_local_files`。
- **系统提示加一段，三四句话**：文件在哪、什么时候写、写结论不抄清单、拿不准写「未确认」、以引擎这次的结果为准。
- **外部 Agent**（Claude Code 等经 MCP 接入的）用自己的文件工具读写，盒子的 MCP 说明里加同样那几句。

### 和另外两套机制的边界

| | 记什么 | 放在哪 |
|---|---|---|
| 经验（[Agent 自然进化](Agent自然进化设计-2026-09-30.md)） | 某个工具报过什么错、后来怎么过的 | 盒子用户目录，贴在工具上 |
| 项目档案（[UE 项目索引](UE项目索引设计-2026-10-14.md)，未实现） | 资产、蓝图、C++ 的结构，机器生成 | 盒子用户目录 |
| **项目知识文件** | 做法、约定、已知问题、为什么这么做 | **项目目录**，人能读、能提交 |

GoldTown 里的「资源包清单」占了 1.35 万字，这是项目档案该干的活。知识文件只写结论，清单交给项目档案。

### 不属于某个项目的资料

比如「UE 资产命名规范」：要反复用的做法写成**技能**，要分享就走共享技能。查完一次就用完的资料，答完即止，不存。

## 旧数据怎么办

那 10 个用户的内容一条都不能丢。

- 升级后第一次启动，把每个知识库导出成一个文件夹：`<文档>/虚幻盒子知识库导出/<库名>/`。每条来源一个 `.md`，网页来源在开头写原链接。
- 旧表不删，只是不再读。等下一个大版本再清。
- 想继续用的用户，把文件夹拖进项目的 `UEBox/` 就接上了。通知里不写这句教程，帮助文档里写。

- Agent：两个知识库工具、`createAgent.ts` 里知识库那段提示（约 2110 行）、会话配置里的 `notebook` 绑定、MCP 宿主会话的 `notebook: 'all'`。
- 文档、i18n、官网和教程里的知识库介绍。官网在隔壁仓库 `uebox-website`。

## 风险

- **往用户工程里写文件。** 只在用户要求后才建 `UEBox/`；建之前在对话里说清楚建在哪。Perforce 工程里文件可能是只读的，写失败就如实告诉用户，不绕过去。
- **知识文件写错，后面被当真。** 页里写最后更新的日期，拿不准的写「未确认」；开场提示统一加一句「以引擎这次的结果为准」。文件在版本库里，改坏了能回退。
- **README 太长，撑大开场。** 助手写 README 时只写目录和要紧约定，细节放分页。开场注入设上限，超出就截断，并提示「完整目录见 `UEBox/README.md`」。
- **10 个在用的用户不满。** 导出保证不丢数据；新方式让项目记忆比原来更好用。值得私信这 10 个人，先问问他们用知识库做什么。
